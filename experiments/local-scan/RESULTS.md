# Local folder rescan benchmark

The scanner previously reopened every audio file on each scan, even when the database already contained it. The index avoids tag/artwork parsing and the no-op insert batch when a file's size and modification time, database path and extracted artwork still match. It has no new dependencies and uses the same code on Windows and Linux.

## Measurements

Windows, bundled Zulu JDK 25, jaudiotagger 3.0.1, SQLite 3.54.1.0. Baseline: `3a7185a`. Candidate: incremental index. These measurements compiled the affected production sources against the installed 1.6.0 dependency classpath; they are not full release-package measurements.

Three alternating pairs of fresh JVM processes, five measured rescans per process (15 samples per variant). Each process first imports the library into an isolated profile, then performs two excluded warmup rescans. Dataset: 300 generated, two-second, mono 44.1 kHz/16-bit PCM WAV files, without tags or artwork, approximately 50.5 MiB total. Filesystem caches are warm. The measured operation is the actual `LocalMediaRepository.scanLocalMedia()`, including traversal, database work, and index loading/saving. Every sample checks all database rows against the initial import, including metadata and ordering timestamps.

| Metric, median | Baseline | Indexed | Reduction |
| --- | ---: | ---: | ---: |
| Wall time | 192.88 ms | 50.80 ms | 73.7% |
| Process CPU time | 250.00 ms | 62.50 ms | 75.0% |
| JVM thread allocations | 3,925,520 B | 1,146,304 B | 70.8% |

| Process pair | Baseline median | Indexed median |
| --- | ---: | ---: |
| 1 | 192.12 ms | 50.68 ms |
| 2 | 213.23 ms | 52.31 ms |
| 3 | 190.21 ms | 49.40 ms |

Raw samples are in `samples.json`. CPU time is process-wide and has Windows timer granularity. Allocation bytes are temporary JVM allocations, not retained heap or total RAM. No startup, playback, download-size or Linux performance gain is claimed. The first scan still parses every file and additionally builds the index; first-scan overhead was not measured. A missing/corrupt index falls back to parsing. Same-size edits with deliberately preserved timestamps cannot be detected by this fingerprint. Existing INSERT OR IGNORE behavior and missing-track removal behavior are unchanged.

## Regression coverage

Eleven focused tests passed: restart reuse, size/mtime changes independently, missing database rows/artwork, path collisions, failed reads, files changing during parsing, unsaved scans, corrupt index and pruning. The reuse test failed with the original always-read behavior before implementation. A fresh review found no important issues. Affected production sources compiled locally; the full Gradle suite was not run locally. Tests are selected by Windows headless CI and Linux x64/arm64 CI.

## Reproduce

Copy this experiment directory to a separate checkout of the baseline as well. In each checkout run:

```
./gradlew -I experiments/local-scan/benchmark.init.gradle writeLocalScanBenchmarkClasspath -PdesktopOnly=true
```

Use absolute classpaths (as generated by Gradle) and JDK 25. Point the runner at the two generated classpath files and a new output directory:

```
python experiments/local-scan/run.py --java /path/to/jdk-25/bin/java --baseline-classpath /baseline/build/local-scan-benchmark-classpath.txt --candidate-classpath /candidate/build/local-scan-benchmark-classpath.txt --output /new/benchmark-directory
```

On Windows use `gradlew.bat` and the path to `java.exe`. The runner creates synthetic audio and separate profiles, alternates ordering and saves every sample and subprocess log. It never uses your library/account profile.
